The constraint I set myself
Zero changes to saga_bench/ to go cloud. The three path functions already took their event log, saga store and lease store as optional arguments, so the cloud layer is just four classes implementing the same methods, passed in instead. If the DynamoDB wrappers vanished tomorrow the benchmark would still run — and that is what makes the numbers trustworthy, because both modes execute literally the same coordination code.

03Coordination strategies — the thing under test
Path A · Orchestration
Permanent coordinator, sequential reverse order. Safe by construction, slow by construction.
Path B · Choreography
No coordinator. Everyone compensates at once. No way to express “wait for Payment”.
Path D · Election + graph
Choreographed until failure, then one elected leader schedules against the dependency graph.

03Path D, Step by Stepwhat one failed saga actually does
1
Forward execution, fully choreographed
Order → Notification → Payment all succeed, then Inventory fails. Up to this instant there is no coordinator anywhere in the system and no lease has been touched — that is the zero-overhead claim, and it is why the happy path costs nothing.
2
On-demand leader election
Every service that hears the failure tries to write a lease row keyed by saga id, conditioned on attribute_not_exists(saga_id). DynamoDB resolves the race for us: exactly one write succeeds, everyone else gets ConditionalCheckFailedException and stands down. No consensus protocol, no quorum — the database already provides the atomic primitive.
3
Graph-aware dispatch
The winner reads the compensation graph and compensates in waves rather than in a line:
wave 1   Order (150ms)  ∥  Payment (800ms)
wave 2   Notification (100ms)  ← released only once Payment clears
Total is 900 ms — the critical path — instead of 1,050 ms summed.
4
If the leader dies mid-rollback
The lease carries a TTL, so it eventually expires and a surviving service acquires it. The new leader reads SagaStore to see which compensations already landed and resumes from there. mark_compensated() is itself conditional, so a duplicate attempt returns false instead of refunding twice — idempotency is enforced by the database, not by hoping.
